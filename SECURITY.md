# Security model — public menu, private admin

This project serves a **public, read-only menu** while keeping the **admin panel
and all credentials out of the published site**.

---

## The constraint that shapes everything

GitHub Pages availability depends on the account plan:

| Goal | Free | Pro | Enterprise Cloud |
| --- | --- | --- | --- |
| Public repo → public site | ✅ | ✅ | ✅ |
| **Private repo → public site** | ❌ | ✅ | ✅ |
| Private repo → **auth-gated** site | ❌ | ❌ | ✅ |

`anvra` is a **personal account**. On **GitHub Free a private repository cannot
publish Pages at all** — and making a currently-public Pages repo private
**automatically unpublishes the live site**.

So "make the repo private" is only safe once you are on **GitHub Pro**. Until
then, the repository must stay public, and security comes from *what gets
published*, not from repository visibility.

> **If you do flip to private on Free**, the menu goes offline immediately.
> If a custom domain is ever attached, remove the DNS records *before* going
> private — a dangling CNAME on an unpublished site invites domain takeover.

---

## What actually protects the project

Repository visibility was never the real control. These are:

1. **The published site contains no admin code.** `admin.html`, `auth.js`,
   `github.js` and the credentials file are never copied into the build, so
   there is no editing surface on the public origin at all. Not hidden — absent.
2. **No credentials are committed.** Sign-in hashes live in
   `src/core/admin-credentials.js`, which is git-ignored. Without it the admin
   panel **fails closed** and refuses every sign-in.
3. **Publishing requires a GitHub token that lives only in one browser.** It is
   never committed and never served. Without it, nobody can change the live site
   regardless of what else they obtain.

Point 3 is the one that matters most: even a full copy of this repository gives
an attacker no way to modify the public menu.

## How publishing works

`.github/workflows/deploy-pages.yml` runs `scripts/verify-public-build.cjs`,
which assembles an **allow-listed** directory and refuses to deploy if anything
unexpected appears. Allow-list, never deny-list — a new admin file added later
is excluded by default rather than published by accident.

Published (13 files): `index.html`, `menu.css`, `menu.js`, `store.js`,
`glossary.js`, `i18n.js`, `config.js`, `menu-fallback.js`, `menu.csv`, and four
images.

The build fails if any of these are true:

- a forbidden file or directory is present (`admin.html`, `auth.js`,
  `github.js`, `admin-credentials.js`, `scripts/`, `.github/`, `package.json`, …)
- output contains `github_pat_…`, `ghp_…`, a private key, `NDDAuth`,
  `NDDGitHub`, `NDD_CREDENTIALS`, or the admin password
- anything references `admin.html`
- an `index.html` reference points outside the build
- an expected menu file is missing

Run the identical check locally before pushing:

```bash
npm run verify:public
```

## Answers to the specific verification questions

**Repository privacy** — cannot be enabled on Free without taking the site
offline. Requires Pro. Not currently a security dependency (see above).

**Pages behaviour** — Pages serves *everything* in the publishing source,
whether or not it is linked. Unlinked ≠ private. This is why the allow-listed
build exists rather than relying on obscurity.

**Generated assets** — `config.js` and `menu-fallback.js` are regenerated by the
admin panel. Their headers are checked for admin path references, and the whole
build is re-scanned on every deploy.

**Links** — the customer page contains no admin link and no reveal gesture. Both
were removed: on a public page they only advertise an entry point.

**Source exposure** — the built site contains no server code, no build config,
no tests, no dependency manifest, and no `.git`. `.nojekyll` is set, so nothing
relies on Jekyll's dotfile filtering.

**Caching** — Pages/CDN caches the *published* artifact only. Because secrets
never enter the artifact, there is nothing to purge. Note the corollary: if a
secret is ever published, cached copies persist after deletion, so treat any
exposure as permanent and rotate.

**Deployment configuration** — the workflow has `contents: read` only; it cannot
write to the repository. Concurrency is capped at one deploy. There is no
cross-repo token, because the private-source pattern is not in use yet.

## Known residual risks

1. **The repository is still public.** Anyone can read the source, including
   `auth.js`. That is acceptable because the source contains no credentials —
   but it does mean the sign-in mechanism is fully understood by an attacker.

2. **Client-side sign-in is not real authorization.** With no backend, the check
   runs in the browser. It stops customers; it does not stop a technical user
   with a copy of the code. The GitHub token is the actual control.

3. **⚠️ The old password is in git history.** Commit `297db2b` contains the
   plaintext password and its hash. Removing the files does not remove history.
   **The password must be rotated** — see below. Anyone who cloned the repo
   before this change already has it.

## Required action: rotate the admin password

The current password is compromised via git history.

```bash
# 1. Choose a new password and generate its hash
node -e "console.log(require('crypto').createHash('sha256').update('ndd-admin-v1:7567587816:NEW_PASSWORD_HERE').digest('hex'))"

# 2. Put it in the git-ignored credentials file
#    src/core/admin-credentials.js
```

Because the file is git-ignored, the new password never enters history.

Optionally, purge the old value from history with `git filter-repo` and a force
push — but rotation is what actually resolves the exposure; history rewriting is
cleanup, and it breaks existing clones.

## Hardening roadmap

| Step | Effect | Cost |
| --- | --- | --- |
| Rotate the password (**do this now**) | Invalidates the leaked credential | free |
| Upgrade to GitHub Pro, make the repo private | Source no longer public | ~$4/mo |
| Two-repo split: private source → public built output, deploy key | Public repo holds only built files | free |
| Real backend with server-side auth | Genuine authorization | hosting cost |

The two-repo pattern is the strongest option that stays free. Use an SSH **deploy
key** scoped to the public repo — `GITHUB_TOKEN` cannot write across
repositories, and a classic PAT would over-grant.
